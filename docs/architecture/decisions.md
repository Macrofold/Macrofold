# Accepted architecture decisions

The [architecture overview](README.md) describes current ownership. This document records the major decisions and their tradeoffs; feature documents own implementation details. [Release status](../status/README.md) and [deployment acceptance](../operations/pre-deployment.md) define what has actually been verified.

## Cost-controlled reusable compute

A Worker is a stable autoscaling execution target, not a machine or a Worktree owner. Callers select an economic offering, dedicated-capacity and sibling-isolation requirements, optional baseline/size, and finite spending and concurrency limits. Internal Hosts supply capacity; HostRuns retain generation-fenced assignment and cleanup ownership. Worktrees and harness-specific Sessions remain durable independently.

The scheduler combines placement eligibility with its existing fair organization turns. A full Worker cannot block an unrelated eligible target, and explicit targeting cannot spill into a different price or security contract. Short SQL claims commit before provider, model, or checkpoint I/O. Shared scheduling facts are computed once per decision; ordered local admission avoids a burst of losing lock contenders without serializing actual execution.

Dedicated compute is charged once per allocation, including retained idle capacity. Resource-priced offerings settle monotonic cumulative meters at accepted rates, not a share determined by accidental physical occupancy. Starting, draining and unconfirmed-stop allocations retain their financial obligations. The current Host implementation is Worker/organization scoped even for non-dedicated pricing; cross-customer physical packing remains a separately validated provider optimization, not a security promise.

Manual pause records graceful intent and drains; automatic idle sleep remains enabled and can wake. Provider Host expiration does not replace the Worker ID. Clean authorized file materializations and compatible live harnesses are independent bounded caches. A verified cold continuation must not depend on a surviving warm process. [Architecture](worker-execution.md), [implementation](../features/execution/workers/implementation.md), [measured evidence](../features/execution/workers/verification.md).

## Separate connector selection from authority

Connector authorization uses an approved tool ceiling and additive organization/workspace/preset/pair rules. Selection defaults narrow authority; a run-only owner exception is explicit and recorded by the server. This avoids proliferating subject types or copying rules into presets. Admission freezes IDs/tools/account bindings, while dispatch rechecks current policy. One parent access version serializes tool and rule edits; listing and previews use persisted state without provider calls. [Connector access](../features/identity-integrations/connection-access.md).

## Customer-agent composition and product setup

A named customer agent is an application record linking existing workspaces, worktrees, presets, sessions and triggers. The [reference app](../../examples/personal-agent/README.md) demonstrates the full lifecycle and durable SDK request IDs without creating a second platform aggregate. Optional file memory remains an editable convention, with provenance and correction/forgetting behavior; database and MCP recipes preserve customer identity outside tool arguments. SQLite and one-process locking keep the starter small; production auth and multi-instance claims belong to the adopting app.

Connector enablement is persisted separately from per-customer account consent and grants. An operator holds a session advisory lock on a dedicated autocommit connection during setup, records uncertain non-idempotent creation before the provider call, and never retries that POST blindly. Serving roles can only read the configured exact toolkit pin. Saved-trigger quotas use a deployment default plus an organization override, with serialized creation and no deletion or disabling when limits are lowered.

OpenRouter discovery can admit new text/tool models under verified pricing and protocol rules; account credentials remain independent. Admission currently requires at least 128,000 context tokens and 8,192 completion tokens to match the native runtime configuration. Smaller native models require a coordinated runtime-limit change, not merely a catalog flag. Decision-only models instead use the separate typed decision capability policy.

## Explicit context uses a separate executor

Direct inference and bounded read-only agents share run identity, authorization, ledger, events and capacity with native agents while keeping distinct payloads and mode dispatch. Decision-model eligibility does not weaken native harness floors. An immutable context snapshot is explicit evidence, never application authority. A small task coordinator composes admitted runs; its allocations constrain the same wallet rather than reserve funds twice. Provider and context ports remain typed, with no general workflow engine or customer-code execution in the service process. See [implementation and rollout](../features/decisions/implementation.md).

## Changelog

- [Worker architecture evolution](changelog/workers.md) records the previous compute model, the intermediate proposal, and the reasons for the implemented autoscaling contract. Deployment and provider acceptance remain separate from design history.

- Hermes, DeepSeek Harness and Pi reuse the existing supervised runtime, gateway and checkpoints. DeepSeek embeds its official agent registry because the convenience SDK cannot resume persisted sessions across processes; [runtime architecture](../features/execution/runtime.md#harness-adapters) records that boundary.

- Native Claude subscription configuration is separate from enablement: provider permission and an isolated controller/tool credential boundary must be established before credential collection or execution. The shared-UID volume PoC does not establish that boundary. See [named connection design](../engineering/testing/named-connections.md).

- Workflow orchestration now hands off after 128 phase advances through the existing PostgreSQL outbox. Queue backoff alone could not fit maximum persistence workloads within provider history limits. Separate orchestration ownership preserves the same native execution and reservation; [the history reference](../features/execution/workflow-history.md) records the budget and recovery tradeoff.
- The launch topology moved from a proposed Railway/E2B/BullMQ stack to Vercel-first hosting, with a standalone SQL poller as the tested control-plane alternative. Provider replacement remains explicit engineering work.
- Implementation replaced proposed restic maintenance VMs, a second Workflow history database, and a universal model proxy with application-owned chunked recovery, existing SQL phase state and a native-protocol metering gateway. These boundaries support exact recovery, revocation and spend accounting.
- Concurrency tests demonstrated a foreign-key lock-upgrade deadlock between checkpoint publication and settlement. Financial projection locks use `FOR NO KEY UPDATE` to coexist with foreign-key `KEY SHARE` locks. The same tests showed batch-wide worker waiting wasting capacity; bounded independent dispatch fixes that measured issue.
- Editor refresh originally overwrote dirty drafts; preserving both draft and original revision makes stale-write rejection reliable. Background live refresh keeps this invariant.
- Dashboard freshness uses indexed current resource stamps and batched pooled reads. This avoids persistent database listeners, shared counter-row contention and an organization event log while making missed-signal reconciliation explicit.
