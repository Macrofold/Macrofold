# Capacity calibration evidence

This is contributor evidence, not a production capacity guarantee. The [scaling guide](../../operations/scaling.md#resource-capacity-settings) owns current deployment settings. Measurements were collected on October 13, 2026 with Node 24.13.0 and disposable PostgreSQL 17. The benchmark uses the real HTTP handlers, authorization, scheduler, provider serialization, SQL persistence and financial settlement, with synthetic accounts and a loopback model endpoint. No paid model or machine was used.

## Decisions

- Raise standalone inference advances from **64 to 256 per process**. All measured bursts completed after the admission fix. At the same 256-request workload, throughput improved from 9.6–12.0 to 14.7–20.3 completions/second with a 20-connection pool. The limit counts active advances, not a promised request rate. A 512-slot/512-request stress case reached 21.4 completions/second and about 20 seconds p95 execution latency: too little throughput gain to make 512 the default.
- Raise the application database pool from **20 to 40 per process**. With 64 simultaneous HTTP callers, 40 improved throughput by 25–32% over 20; 80 was slower than 40. With 256 callers and 2,048 requests, 40 reduced p95 latency from 3.07 to 1.42 seconds. The synthetic model path did not show a consistent benefit from 40; use an explicit smaller worker pool when its measured workload benefits. All process types must share a deployment connection budget.
- Keep auth **5** and credential **4**. Valid session-authenticated API tests showed no gain at 10/20 auth connections. Nested credential transactions completed over 1,000 times/second with four connections; 8/16 did not improve p95. These are short SQL transactions, not a cap on active users or model HTTP sockets.
- Retain the independent native, transfer, maintenance, plan and queue controls described below. A functional boundary test does not determine the best quota or justify buying hundreds of machines. Their production tuning remains distinct from the measured in-process defaults.

## Progress defects discovered

The original dispatcher completed only **9 of 128** accepted one-second model requests in 180 seconds. Ordering the returned rows alone completed only one in that window. Concurrent attempts repeatedly competed for organization/global locks and could defeat the eligible fair head; `UPDATE ... RETURNING` also lost the ordered candidate selection.

Ordered, sequential **SQL admission only**, followed by concurrent execution, completed all 128 in **13.88 seconds**, with 128 unique usage records and no remaining reservations. The portable, simulator and Workflow paths now preserve candidate order. Model calls, uploads and machine operations remain concurrent; financial locks and execution fences remain intact. Multi-dispatcher regression tests protect progress and single billing.

The simulator's separate prepare/send/settle path also left the admission recovery deadline in place after an unfinished advance. A competing-dispatcher test completed only 60 of 64 requests within its window. Scheduling the next ready phase from its returned delay fixes that idle gap; all 64 now finish with one provider request and usage row each.

## Method and results

[Machine-readable measurements](evidence.json) include failures as well as valid runs. Series are sequential within each matrix; each case runs in a fresh process and, after the pilot, a fresh cloned database. Queue construction and HTTP warmup are outside the timed dispatch/request section. End-to-end Run latency includes queue time where reported. Execution p95 below starts at Run claim, not at HTTP submission.

The database container had two CPUs, 1 GiB RAM and 300 allowed connections. The Docker VM and host also served an existing preview, which was not stopped. This introduces real timing variance; these numbers are not confidence intervals or measurements of a hosted database. The disposable database, filesystem and request content are independent of the preview. Higher fleet defaults are not derived from this machine's Docker limits.

The selected defaults also completed a sustained **10,000-request API workload** with 256 callers: 259.9 requests/second, p95 1,663 ms, p99 2,258 ms and zero errors. A **1,024-inference burst** with 256 slots drained in 64.21 seconds after 17.21 seconds of queue construction, with exactly 1,024 provider calls, 1,024 distinct usage rows and no remaining reservations. Execution p95 was 18.15 seconds; end-to-end p95, including queue time, was 64.11 seconds. This exposes the throughput/queueing cost of a burst larger than one process's active pool; it is not a low-latency guarantee for 1,024 simultaneous requests.

Measured process RSS across successful request cases reached 664 MiB in the sustained API workload and 464 MiB in the larger inference case. Payloads were small; this is **not** a memory bound for maximum-size prompts, outputs, media or streams. Inference event-loop p99 reached 66.5 ms. Requests waiting for a SQL connection still occur under bursts; no acquisition deadline was reached in successful benchmark cases. Larger pools do not remove row-lock contention or the cost of scheduling and settlement.

[Restore/planner measurements](io-evidence.json) support retaining the eight-step transfer pool: 128 MiB of verified restoration took 1,356/714/674 ms at 4/8/16 simultaneous steps. Doubling eight to sixteen provided only about 6% more throughput with this latency/payload. Observed process RSS was 308/590/741 MiB; these cases share a process, so heap retention means the difference is not a clean incremental-memory measurement. Reads/decryption/hashes are real; storage and machine uploads have synthetic 20 ms latency. Planning for 1,000/10,000 demands took 10.5/72.5 ms and honored the 16-new-Host budget. None of these numbers measures cloud-machine provisioning.

The first session benchmark omitted the browser Origin header. Mutation requests correctly returned 403; that series is marked invalid for tuning and was rerun with the real browser contract. An initial regression run inherited the developer's ten-native-run override; fixture setup now assigns all three fleet ceilings explicitly. Neither failure is counted as a capacity pass.

The native occupancy test initially timed out because unnamed fixture Worktrees caused 201 Git checkpoints during Run admission. Named, distinct metadata fixtures isolate the SQL boundary; the final test admits 200 and queues the excess. This is not a measurement of 200 actual machine starts or a claim that mass Worktree initialization is instantaneous.

## Reproduce

Use a dedicated disposable PostgreSQL instance and the repository's supported Node version. Do not point these commands at a deployed database. The test wrapper creates and removes isolated databases; it needs an owner connection only for that setup.

```sh
docker run --rm -d --name macrofold-capacity \
  --cpus=2 --memory=1g --shm-size=256m \
  -p 127.0.0.1:60233:5432 \
  -e POSTGRES_USER=platform_owner -e POSTGRES_PASSWORD=capacity-fixture-only \
  -e POSTGRES_DB=platform postgres:17-alpine \
  -c max_connections=300 -c shared_buffers=128MB

export PLATFORM_MODE=local EXECUTION_PROVIDER=simulator ALLOW_PAID_EXECUTION=false
export DATABASE_URL=postgres://platform_app:local-app-only@127.0.0.1:60233/platform
export MIGRATION_DATABASE_URL=postgres://platform_owner:capacity-fixture-only@127.0.0.1:60233/platform
pnpm exec tsx scripts/capacity.ts
pnpm test:domain tests/load tests/integration/portable-dispatch.test.ts \
  tests/integration/database-capacity.test.ts tests/unit/resource-capacity.test.ts \
  tests/unit/worker-scaling.test.ts tests/unit/execution-hydration.test.ts \
  tests/unit/poller-loop.test.ts
docker stop macrofold-capacity
```

The [benchmark script](../../../scripts/capacity.ts) writes private JSONL under `.data/capacity-*`. Override `CAPACITY_CASES` with an array of `{mode, pool, concurrency, count, delay?}`: modes are `http`, `session`, `credential`, and `inference`; `delay` is synthetic provider milliseconds. `pool` selects the relevant pool for that mode. `CAPACITY_OUTPUT` selects the report directory. Inference fixtures enable execution only in the disposable child after intercepting provider fetches; unexpected outbound fetches fail. They never use a real provider key.

For the larger acceptance cases, set `CAPACITY_CASES='[{"mode":"http","pool":40,"concurrency":256,"count":10000},{"mode":"inference","pool":40,"concurrency":256,"count":1024,"delay":1000}]'`. For visible per-case restore/planner measurements, add `--reporter=verbose --disableConsoleIntercept` to their `pnpm test:domain` invocation.

## Verification and remaining work

The evidence contains 34 HTTP/database/inference scenarios, of which 28 are valid for tuning; failed or diagnostic pilot scenarios remain explicitly marked. The final Run/queue/fleet/restore/planner/inference regression slice passed **95/95** tests. The restore/planner/GitHub integration slice passed **39/39**. A shuffled scheduling/capacity/webhook slice also passed **16/16**, including real independent worker processes and crash recovery (`--sequence.shuffle.files --sequence.seed=20261013`). Separate slices passed Workflow dispatch, portable resource pools, real DB acquisition expiry/recovery, maintenance, storage, webhook, trigger, OAuth and Worker regressions. These slices overlap; their counts must not be summed as unique tests. TypeScript/app SDK build (`pnpm check`), documentation checks and diff whitespace checks pass.

No paid execution, hosted load test, production deployment or restart of the existing preview/worker was performed. Existing processes must restart to use the new defaults and scheduling fixes. No schema or runtime-image change is needed for this calibration.

Before promising hosted capacity, repeat representative prompts, output sizes, slow/failing providers, native starts, remote storage and retained-history workloads on staging. Record provider quotas, per-replica connection use, CPU/memory, queue-age fairness, errors and sustained throughput. Deployment roll-out remains in [maintainer work](../../maintainers/TODO.md#resource-capacity-and-progress).
