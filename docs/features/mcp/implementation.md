# Customer MCP architecture

The route [`/mcp`](../../../apps/web/app/mcp/route.ts) uses the official TypeScript SDK's stateless Streamable HTTP transport. The installed SDK negotiates the 2025-11-25 protocol and its supported earlier revisions. This implementation does not claim the newer 2026 stateless wire protocol; client metadata registration uses the maintained Better Auth CIMD plugin's 2026 profile independently of JSON-RPC negotiation.

## Ownership

- [`customer-mcp-catalog.ts`](../../../packages/core/src/customer-mcp-catalog.ts) derives tools and reachable JSON Schema definitions from the same [OpenAPI contract](../../api/openapi.json) as REST validation and generated SDKs. Explicit exclusions cover only the two SSE transports. A coverage test fails when an API operation disappears from the catalog.
- [`customer-mcp.ts`](../../../packages/core/src/customer-mcp.ts) owns transport, bounded inputs/results, pagination, and MCP result/error shapes. It translates a known operation to an internal Request and calls the existing [`handleApi`](../../../packages/core/src/http.ts) application pipeline. It does not fetch a caller-provided URL or duplicate resource handlers.
- The Next.js route schedules the existing durable outbox dispatcher after successful mutations, matching REST admission. The core transport reports accepted mutations through a callback; it does not depend on Next.js or start background jobs during discovery or reads.
- [`auth.ts`](../../../packages/core/src/auth.ts) owns authentication and audience/resource validation. OAuth tokens for `/mcp` are distinct from `/v1` and `/admin/mcp`; scoped customer API keys work on either customer interface. Browser cookies alone never authenticate MCP requests. Origin checks reject foreign browser origins.
- Resource authorization, tenant RLS, budgets, permissions, idempotency, rate limits, audit, and observation remain in their existing owners. Accepted OAuth runs retain their admission audience so delegated authorization checks use the correct resource; explicit revocation still takes effect.

## Security and compatibility

Unauthenticated requests return a 401 Bearer challenge linking to `/.well-known/oauth-protected-resource/mcp`. Authorization uses PKCE S256, exact registered redirects, issuer/resource checks and user consent. CIMD uses the existing [`safeFetch`](../../../packages/providers/src/network.ts) adapter for public-address validation, DNS pinning and redirect refusal; the plugin retains metadata validation, its five-second deadline and 5 KiB response limit. Conditional HTTP 304 responses preserve validated metadata caching. This avoids the pinned library's Node transport incompatibility with Node 24's multi-address DNS callback. Dynamic registration remains available for existing clients, can register only customer scopes/resources, and cannot register an operator client. Native loopback registrations must declare their native application type.

The server is stateless; it issues no MCP session ID and does not hold an SSE listener. Long work is represented by durable platform run/operation IDs. GET/DELETE return 405 after authentication. Tool discovery pages by 50 and filters scopes; direct tool calls still enforce the real authorization policy. Tool annotations are conservative hints only. All mutation calls require idempotency keys, including operations for which REST makes the key optional.

MCP request and JSON response bodies are bounded at 1 MiB; inline file contents are bounded at 64 KiB. Larger file transfers use the existing private transfer capabilities. Errors include the REST status, sanitized error, and request ID when available. Tool output remains untrusted data. Secret-creating operations are exposed because they are customer API operations; instructions explicitly require user intent and secret handling. Do not log entire tool results.

## Verification and tradeoffs

Unit tests exercise contract coverage, recursive definitions, validation, header/path/query translation, binary bounds, conditional metadata responses and private-address/redirect rejection. Disposable PostgreSQL tests use the official MCP client for initialization, pagination, workspace/run creation, duplicate protection, results, continuation, cross-tenant denial, role/scope restrictions, both DCR and CIMD registration, OAuth PKCE consent, wrong-audience denial and grant revocation. A separate dispatch test checks that accepted mutations notify the hosting layer while reads, initialization and rejected mutations do not. The operator MCP remains read-only. A manual loopback HTTP journey using the official client discovered all 132 tools, created a workspace, completed a simulator run, and verified duplicate submission reuse without paid provider calls.

A broad catalog favors API completeness and consistent names. Clients should use tool search/lazy discovery when available; no additional generic `execute` tool bypasses per-operation schemas. A curated smaller default toolset can be added later if measured client context limits justify it. Binary tools deliberately avoid large inline output and custom UI/resource rendering.

The isolated MCP release is deployed at `https://app.macrofold.ai/mcp`, with live health, protected-resource metadata, unauthenticated denial and browser-rendered setup documentation verified. Production authorization fetches Codex’s real client metadata; browser sign-in/consent, global Codex OAuth configuration, tool discovery and an authenticated `listWorkspaces` call returning HTTP 200 pass in the desktop session. Production mutations and paid execution remain unverified. Codex’s initial scope selection includes the shared issuer’s operator scopes, so the public setup command selects customer scopes explicitly. See [release TODO](../../maintainers/TODO.md).
