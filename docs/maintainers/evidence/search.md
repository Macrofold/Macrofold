# Search integration verification

[Adapter unit tests](../../../tests/unit/search.test.ts) exercise all five public wire formats, result normalization, empty/malformed data, selected credentials, bounded output, failure responses, cancellation and timeouts without calling vendors. [API tests](../../../tests/integration/search-connections.test.ts) exercise persisted connections, encrypted keys, tenant boundaries, grants and forbidden managed modes. [Broker tests](../../../tests/integration/tool-broker.test.ts) exercise dispatch and replay with local PostgreSQL and intercepted transport. [Dashboard acceptance](../../../tests/browser/search-providers.spec.ts) covers provider selection, key clearing, persisted connections and grants.

These are deterministic local checks, not successful authenticated vendor integrations. Before enabling a provider for customers, complete its bounded authenticated search, quota/error, runtime-MCP and invoice checks in the [pre-deployment checklist](../../operations/pre-deployment.md). No new package, hosted service or account is required for the adapters themselves; vendor usage and existing compute remain chargeable.

Scoped acceptance passes 76 unit/integration/catalog cases, including 55 search unit cases. Each of the four new providers passes its dashboard journey and accessibility scan across targeted runs against a separate local development server with synthetic accounts. Batch attempts also encountered preview timeouts and one generic connection-creation 500; a clean complete browser run against a stable production build remains required. These checks establish functional provider selection and broker behavior, not production latency or load capacity. TypeScript, generated contracts and documentation links are checked separately from live vendor acceptance.
